# 种类推断与高阶合一

**状态**：候选
**一句话**：构造子也由推断给出——`def collapse<F<_>> xs: F<Int>` 成立，`Map<K, _>` 这类部分应用可用，调用点自己决定 F 是什么。

**动机**：种类参数写死在声明里，等于每种容器派生一套 trait。推断一旦打开，用户可以写真正的泛型算法（对任意容器折叠、对任意二元容器 zip），库的复用面大幅上升。

**形态**（若采用）：

```
def collapse<F<_>> xs: F<Int> -> List<Int> = ...
trait BiFunctor<F<_, _>> { ... }        # 二元构造子可用

Map<Text, _>                             # 部分应用作为类型
```

**代价**：

- **高阶合一**：推断 `F` 需要解形如 `F<A> = Map<Text, Int>` 的方程，解不唯一、可能发散，错误信息质量骤降。
- **编译时间**：合一本身不是不动点，但高阶合一在实践中常需要迭代与回溯，越界就变成「试一遍所有构造子」。
- **规格**：「一个人能读完」的规格里不能再写「种类不推断」这一条简化。

这是设计里最典型的一处「表达力 vs 编译器成本」交易，两边都可以说。
