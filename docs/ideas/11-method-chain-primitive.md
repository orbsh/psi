# 调用只有一个原语：接收者 + 名字 + arity 个实参

**状态**：在用（可改）
**一句话**：整个语言的调用面压成一件事——一个接收者、一个方法名、声明规定数量的实参；管道、中缀、运算、模块都是这条的记法，不是另外的机制。

**动机**：展开目标只有一个，解析规则就能写成几条固定规则；每多一个展开目标（`+` 走一套、`for` 走一套、`map` 走一套），规则数量就随特性相乘。这也是与 Scala 的分界线：Scala 的核心语义同样是方法调用加多层糖，但每种糖各管一段。

**形态**：

```
x.trim                  # 零参调用
x.replace "a" "b"       # 两参调用：replace 的声明有两个参数
xs.map {x| x * 2}       # 块是普通实参
```

```
chain   = primary step* '?'?
step    = '.' name              # 取方法；其后必须紧跟 arity 个实参步
        | primary               # 一个实参
```

四条解析规则：

- **每步作用于整条前缀**：`x.f` 作用在 `x` 上，`a b` 里的 `b` 作用在 `a` 上。
- **arity 决定消费几个步**：被调用者声明 N 个参数就吃掉紧随的 N 个 primary 步；不够是「参数不足」，多出来的步作用在结果上。`a b c` 在 `a` 一参时是 `(a b) c`，两参时是一次二元调用。
- **实参是 primary**：name、字面量、括号、块、记录。要传完整表达式写括号。
- **中缀最松**：应用比中缀紧，中缀按首字符定级。

读法实例（左 → 唯一读法）：

- `x.f a b`（f 两参）→ 一次二元调用
- `x.f a b.c`（f 两参）→ `(x.f a b).c`
- `xs.map f.filter p` → `(xs.map f).filter p`——链跨过实参继续，流畅 API 成立的原因
- `a.x b.y z`（x 两参）→ 编译错误：`.y` 打断了 `x` 的实参位
- `f a.b`（f 一参）→ `(f a).b`——`.` 永远作用于整条前缀
- `a + b c` → `a + (b c)`；`a + b * c` → `a + (b * c)`
- `a + b ▷ {x| x}` → `(a + b) ▷ {x| x}`——符号名进中缀位
- `a + b y {x| x}` → `a + ((b y) {x| x})`——字母名只能站实参位

**代价**：arg 分组依赖声明，读代码时局部信息不够——`a b c` 的含义要知道 `a` 的 arity 才能定，而这要么来自同一个文件，要么来自导入。全程序编译把这件事摊平了，但在屏幕上读一个片段时它不成立。真正的代价在错误信息：参数不足的报错位置会落在链尾而不是调用点。

**冲突**：[12](12-arity-grouping.md) 说的是这个原语的记法（不带括号）；换记法（括号 + 逗号）会保留 `arity` 概念但改变分组规则。[13](13-infix-by-spelling.md) 是它的中缀记法。[14](14-no-pipe.md) 说管道就是这个原语，[15](15-pipe-operator.md) 说要另设符号。若 [16](16-methods-are-not-values.md) 反过来（方法成为值），这条原语要再加一套「名字在表达式里表示什么」的规则。
