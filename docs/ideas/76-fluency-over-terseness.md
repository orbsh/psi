# 流畅性优先于简洁

**状态**：在用
**一句话**：语法取舍的第一判据是读写的流畅性——写的时候手不停，读的时候主语不断；「简洁」（更少记号）与「简单」（更少机制）都不是判据，与流畅性冲突时让位。

**动机**：语法设计里最容易误用的目标是简洁。它可量化——字符数、关键字数、规则数，于是容易被当成指标去优化；但它与流畅并不同向，甚至在多数点上反向。

三个词要分开：

- **简单**是机制少：一个原语、一条展开路径、不设第二套写法。
- **简洁**是记号少：省括号、省分号、省关键字、省类型标注。
- **流畅**是读写不中断：写的时候不必停下来做选择，读的时候不必回头去别处取信息。

省括号是最清楚的例子。`x.replace "a" "b"` 比 `x.replace("a", "b")` 少四个字符，代价是分组的依据从「眼前这对括号」变成「`replace` 的声明里有几个参数」——读者必须知道别处的一个事实才能确定这句话怎么解析。这把成本从写的人挪到了读的人，而读的次数远多于写。

反过来，`let` 比裸 `x = e` 多三个字符，消掉的是「这是绑定还是赋值」的一次读回。分号多一个字符，消掉的是「换行算不算语句结束」的上下文判断。这两个都是拿记号换流畅，而不是拿记号换简洁。

**形态**：判据展开成四条，按优先级：

1. **主语不断**：一句话以数据开头，动词沿链往下走。`x.trim().replace("a", "b").len()` 是对的；`len(replace(trim(x), "a", "b"))` 即使更短也不流畅，主语被埋进参数里。
2. **手不停**：常见动作只有一种写法。两种等价形式并存（`f(x)` 与 `f x`）本身就是摩擦——每次都要决定用哪个，决定就是停顿。
3. **不回看**：读一段代码，不需要知道别处的声明才能确定它怎么解析。分组靠括号（就地可见），不靠被调用方的 arity。
4. **不打断视线**：噪音只保留有信息量的。`&`、`*`、生命周期标记、`::<>` 在 Rust 里的痛不是长度，是每次出现都要重新推理一遍归属。

裁决顺序：**流畅性 > 零惊异 > 机制数 > 记号数**。

零惊异的位置要说明：它是流畅性的边界条件，不是第二目标。发明一套更好的记法可以换来流畅，但读者要为此重学一遍，净收益经常是负的——所以新的记法只在旧记法真的挡住流畅时才引入。反过来，零惊异也让位：Rust 的皮之所以可以直接照抄，正因为 ψ 不继承 Rust 最痛的那三样（引用、生命周期、借用检查），照抄不会连带它们。

**代价**：

- **判据主观**。流畅性没有度量，最终靠读代码的人拍板。这条想法把裁决权交给人，而不是交给一条可计算的规则；两个人对「读起来顺」判断不同时，没有更高的裁判。
- **与机制数冲突时留了口子**。「常见动作只有一种写法」是好判据，但为了停留在一个原语上，可以留下两种表面形态（例如 `if` 与 `match` 都能作表达式），所以机制数不是硬上限。
- **代码看起来会更啰嗦**。第 3 条与第 4 条合起来意味着括号、类型标注、`self` 都会留着；用极简标准衡量，这套表面是胖的。这是有意的：胖在明处，瘦在暗处。
