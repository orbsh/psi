# 注记一律后缀，因为删除只能影响后缀

**状态**：在用

**一句话**：声明句的槽位由删除安全性决定——句型词在最左，锚点次之，可省略的注记一律后缀；最左位留给最能压缩后续解析空间的记号。

**动机**：常见的说法是「确定的放前面、可变的放后面」，那是观察，不是机制。它解释不了为什么 Rust 的函数参数类型不能推断却依然写在名字后面，也解释不了 `impl Trait for T` 为什么把类型放在最左。

真正的机制只有两条，都可检查：

- **删除测试**：把可省略的部分删掉，剩下的前缀必须仍然合法且同义。`let a: Int = 5` 删掉类型得 `let a = 5`，成立；`int a = 5` 删掉类型得 `a = 5`，与赋值语句撞车。所以可省略的东西只能在后缀位。
- **最左决定读法**：第一个记号要单独决定「这是什么句型」。`let`、`fn`、`pub`、`SELECT` 站在最左，因为它们决定后面怎么读；C 的 `int` 同时是类型名和句型开关，于是 `int a` 与 `a * b;` 只能靠更长的前缀区分。

因果方向要摆正：不是「类型可以推断，所以放到后面」，而是「放在后面，省略才是安全的」。Rust 的函数参数类型不可推断、必须写，位置照旧在后；`where` 子句、`impl Trait` 同理。位置的统一与可推断性无关，可推断性只决定这条位置规则能不能兑现成省略。

**形态**：三个槽，次序固定。

- **句型词**：`let`、`fn`、`pub`、`struct`、`for`——决定怎么读，必须在最左。
- **锚点**：名字；赋值句里是目标位置。读者要抓的那个实体。
- **注记**：类型、区域约束、effect、`where`、返回值类型——可省、可推导、长度不定，一律后缀，按固定次序排列。

锚点不总是名字。派发句的锚点是类型：`impl Display for Circle` 把类型排在前面，因为这里要选的是「哪条规则」，最具选择性的键是类型。同理，函数签名里的 `-> T` 是注记不是目标，所以它在最后——这与「赋值的输出在前」不矛盾，因为一个是句型（声明）的槽位，一个是数据流的方向。

判据一句话：**最左位留给最能压缩后续解析空间的记号**。确定性只是它的一个表现。

**适用边界**（说明它是启发式，不是定律）：

- 前提是顺序读取与单遍解析。可以随机访问的格式不受约束——Parquet 把 schema 放在文件尾，因为读文件能 seek。
- SQL 违反这条：动词在最左，锚点（表）在后面，投影列夹在中间。这是历史选择，也是它心智负担的来源。
- 两套次序并存是常态，不是异常：x86 汇编的 Intel 与 AT&T 两种操作数次序都还活着，AT&T 的源在前来自 PDP-11 汇编器照机器编码顺序写，与「数据流向哲学」无关。
- 真实指令集里「唯一输出」也不成立：`mul` 写 `rdx:rax`，`rdtsc` 写 `edx:eax`。三地址 RISC 才是真正的一目标多源。

**代价**：

- **句式变长**。前置风格在短句里更省，`int a` 比 `let a: Int` 短。
- **同一个记号在不同句型里位置不同**。返回类型在后、赋值目标在前，读者要把两条规则都记住；这比「一切都是前缀」需要多一次确认。
- **遇到 C 式声明符语法的等价物就无解**。`int (*f(int))(void)` 把名字埋在最深处，类型前置加上声明符叠加，任何槽位规则都救不了；后置语言之所以成立，前提是类型本身不需要声明符语法。
- **它不是原则，是两条原则的合并**。删掉任一条都能找到反例，所以引用它时必须说清用的是哪一条。

**冲突**：与 [76](76-fluency-over-terseness.md) 分工不冲突——76 管链内次序（主语不断、动词沿链），本条管声明句的槽位次序。与 [75](75-rust-surface-syntax.md) 相关：照抄 Rust 表面时，凡是次序选择都按本条核一次，不按「Rust 这么写」照收。
