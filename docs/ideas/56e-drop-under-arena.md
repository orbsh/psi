# 区域里的 Drop：清理链，不是逐值析构

**状态**：候选
**一句话**：arena 的死亡时机是「区域退出」，Rust 的 Drop 时机是「值离开作用域」；两者能对齐的唯一办法是每个区域维护一条清理链，退出时反序执行，然后整块擦除。

**动机**：Rust 风格的 `impl Drop` 是那套语法里最有用的一半（关文件、释放句柄、断开连接）。区域模型若没有它，所有资源释放都要手写；若有它但不能在区域里工作，就只剩「内存擦除」这一种死亡，外部资源无从管理。

## 形态

```
struct File {
  handle: HostFd
  def drop = Host.close self.handle    # 唯一需要跑代码的析构
}

f() {
  let a = File.open "x"
  let b = File.open "y"
}     # 反序：b 先 close，再 a，然后整块擦除
```

三件事同时成立才叫「优雅」：

- **编译期就知道这个区域要不要走清理链**：类型带 `needs_drop` 位（rustc 也有这个），区域类型同样带一位。整个区域都是纯数据 → 退出时只做 `sp -= size`，仍是 O(1)。
- **登记是侵入式的**：可析构对象在分配时挂一个链节点（一个字），区域退出时走一遍链。代价是 k 个字 + O(k) 反序调用，k = 该区域内可析构对象的个数。
- **析构体只能看自己和宿主句柄**：禁止访问同区域的其它对象。反序执行时，晚分配的对象已经析构完了，互指就会 use-after-drop——Rust 靠借用检查排除这一点，这里用一条更便宜的可静态检查规则替代。

## 代价（结构性的部分）

- **时机粒度就是区域粒度**：Rust 的 Drop 跟着每个 `{}` 走（含每一条 early-return / panic 路径），要对齐就得让每个作用域都开子区域，区域数按作用域数膨胀，长尾膨胀回来。所以这条实现的是「区域退出统一清理」，不是「值离开作用域就清理」——**函数中间失败时，资源要等到区域结束才关**。
- **清理链破坏「一次指针回退」**：有析构的区域退出去不是一条指令，是一次遍历。常态（纯数据区域）不受影响，热路径里如果混进可析构对象就要付。
- **析构体可能 panic 或失败**：`close` 失败怎么报？区域退出时没有返回值可给。要么忽略（Go 的 `defer f.Close()` 老问题），要么收集成区域级错误列表。

## 更省的一条路：资源不进区域

内存对象的死亡不需要 Drop（擦除就是死亡）。真正需要跑代码的只有**外部资源**：文件、socket、wasm 句柄。而外部资源的正确生命期往往不是「这段代码的作用域」，是「谁持有它」。

所以另一种形态是：`Drop` 只显式实现给资源句柄类型，句柄自己进一个专门的 resource 区域（进程级或请求级），释放走 `defer` / 显式 `close`，与内存层级分开。这样区域继续 O(1)，资源释放的时机由代码写出来而不是由区域猜。
