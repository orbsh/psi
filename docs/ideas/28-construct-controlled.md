# 构造受控：字段默认模块私有

**状态**：未定
**一句话**：`Circle { radius: ... }` 这种字面量构造只允许在定义 `Circle` 的模块内写，外部只能走导出的构造函数。

**动机**：Parse, Don't Validate 在语法上唯一的抓手。现在 parse 造出的值和手搓的值同类型、同构造方式，「边界解析一次、内部不再校验」就落不了地——任何代码都能在内部伪造一个「已经通过校验」的值。

**形态**（若采用）：

```
struct Email {
  let value: Text        # 模块私有可构造
  @export def parse s: Text -> Result<Email, Text> = ...
}

Email { value: "x" }     # 其他模块：编译错误
Email.parse "x"          # 唯一入口
```

有两种强度可选：字段私有但模块内可随意构造（弱）；或连模块内也只能走构造函数（强，需要「该直接构造只出现在构造函数里」的检查）。

**代价**：

- 少一个最有用的便利：测试里造 fixture 要绕一圈（要么导出一个 `unsafe` 构造函数，要么语言给测试开例外）。
- 与 [21](21-unified-dot-access.md) 的对称性被打破：读字段公开、写字段私有，可见性变成两个轴。
- 需要一套可见性语法，而这条语言目前没有 `pub`/`private`——加它就是加一类声明修饰，与「语法一页写完」有摩擦。

**冲突**：[29](29-data-first-levers.md) 把它列为「还缺的硬杠杆」；反过来 [63](63-value-semantics.md) 的不可变性已经消掉了一半问题（值造出来之后没人能改它，伪造的只是一个合法形状的值，不是非法状态）。

**若改掉会动到**：[21](21-unified-dot-access.md)、声明语法（要加可见性）、[41](41-json-boundary.md)（边界类型是否都要包成不让构造的 newtype）。
