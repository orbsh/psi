# 继承与线性化

**状态**：候选
**一句话**：类型可以有父类型，方法解析沿父链查找，多重继承用 C3 线性化定顺序，`super` 调用父实现。

**动机**：继承把「一组方法 + 一份字段」打包复用，是一个类型对另一个类型最直接的复用。对一个要写业务模型的语言，`Circle is-a Shape` 这类关系比 `impl` 附着更贴近直觉，而且字段复用不用手写转发。另外子类型关系带来 upcast：`List<Shape>` 能收 `Circle`，里氏替换可用。

**形态**（若采用）：

```
class Shape { def area -> Float = 0.0 }
class Circle(r: Float) : Shape { def area -> Float = 3.14159 * r * r }

shapes: List<Shape> = [Circle 1.0, Rect 2.0 3.0]   # upcast
```

**代价**：

- **引入派发顺序这一维**：多重继承要有线性化（C3），`super` 的语义随之变得依赖类的声明顺序。这是 ψ 在 [31](31-tags-not-trees.md) 里刻意不进的那个维度。
- **一个类型只占一个位置**：分类压力集中到父链上，想「同时是 Shape 和 Serializable」只能靠接口（于是退回标签模型）或继续加深树。
- **脆弱基类**：父类加一个方法，子类里同名的东西被静默遮蔽。
- **表达式问题的一轴被关**：加一个操作要么改父类，要么在子类里复制。

**冲突**：[31](31-tags-not-trees.md) 正面冲突。可以混合（单继承 + 多接口），那时两者的账都要付。
