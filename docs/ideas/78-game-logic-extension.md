# 宿主是游戏逻辑扩展：事件、条件、动作

**状态**：候选

**一句话**：ψ 要嵌的位置是 WC3 地图编辑器那种扩展机制——地图作者注册事件、写条件与动作——不是"某个宿主里调一次函数"的通用脚本。

**动机**：这类生态的需求形状与嵌入式脚本不同，四点决定语言与运行时的形态。

- **多而小**：几十到几百个扩展同时驻留，每个只关心几个事件，代码总量不大，加载与卸载频繁。
- **触发式而非调用式**：脚本不进主循环，主循环在特定时刻"问"脚本。进入点由事件决定，不由代码结构决定。
- **不可信**：作者是外部人，脚本不能崩宿主、不能无限跑、不能读别人的状态。
- **确定性**：同一局的回放要一致，事件顺序必须由规则定死，不能由调度器的竞争决定。

**形态**：

- **触发是三元组**：(事件, 条件, 动作)。扩展注册进宿主的订阅表，宿主在事件发生时按注册序求值条件、执行动作。
- **粒度是地图/对局，不是单位**。每个实体一个脚本实例等于每个实体一次投递：一次进程内投递是 µs 量级（排队、路由、上下文组装），一万个实体按 60Hz 就是每帧 10ms，而帧预算只有 16.6ms，全部耗在投递上。实体级的批量计算归宿主的数据数组，不归脚本。
- **每 tick 进入一次，脚本内部批量扫**。宿主给的是查询面与修改意图（"这一批筛选出的单位受 100 点伤害"），不是实体句柄。
- **帧内状态不归脚本**。位置、血量、冷却住在宿主的连续数组里；脚本只持有规则与跨帧少量状态。逐帧把实体状态写进键值存储是 µs 级操作，一次一小片就把帧预算吃穿。
- **沙箱是三件事**：导入表按扩展裁剪（能力面）、执行配额按指令数与分配字节数记（不是按墙钟时间，否则不确定）、状态读写限定在自己的命名空间。
- **顺序由注册序定**，明确写进契约。调度器不参与排序，否则回放不可复现。

**代价**：

- **事件风暴要自己合并**。同帧上千个单位死亡会触发上千次条件求值；宿主必须提供批量事件与去重，否则触发器层自己就是瓶颈。
- **脚本拿不到实体句柄**，查询面必须设计成批量接口，作者写不出"遍历所有单位一个个改"的代码。这是能力面的收窄，会一直被要求放宽。
- **扩展升级与存档脱钩**：存档里只能放稳定 id 与版本号，不能放脚本内部结构。
- **热重载要求状态迁移**：脚本可换，状态不可丢，跨版本的迁移责任落回扩展作者。
