# 载体是自建字节码，由自带 VM 执行

**状态**：候选

**一句话**：产物不再是标准 wasm 模块，而是私有字节码，由语言自带的解释器执行；脚本是数据，不是模块。

**动机**：三个需求同时指向同一形态。

- **脚本即数据**。游戏扩展生态里几百个 mod 同时驻留，每个只订阅几个事件，要热重载、要按 mod 裁剪权限。wasm 下每个脚本是一个模块实例：跨模块调用要过 glue 或组件模型，实例化有成本，热重载是换实例加状态迁移。字节码下它们是同一个地址空间里的 blob，调用是一次间接调用，热重载是换一个表项，沙箱是换一张导入表。
- **内存布局自主**。无 GC、区域批量回收、记录内联在帧里，这些要求语言拥有分配器与对象布局。wasm-gc 一层都不提供（[54](54-wasm-gc.md) 已写明）。
- **平台合规**。游戏机与 iOS 禁止运行期生成代码，那里没有 JIT，wasm 引擎也多是解释或 AOT 实现。字节码 + 解释器是这些平台的唯一天然形态，不是降级方案。

**形态**：

- 一份类型化 IR，两个发射器：字节码（默认）与 wasm（浏览器与外部工具链）。不是两门语言，是同一 IR 的两条出口。
- 脚本是字节码 blob，宿主一次加载进同一个 VM；导出按名字查表；调用是间接调用，不经过宿主语言的胶水层。
- 指令集是寄存器式，不是栈式（见 [79](79-batch-opcodes.md)）。栈式每个操作要 push/pop，寄存器式实测少执行约 47% 的指令（Shi et al., VEE'05；SPE 2025 复核）。
- 内存无 GC：分配器随调用入口传入（Odin 的 `context.allocator` 形状），区域负责批量回收；帧内状态留在宿主数组里，不进脚本堆。
- 可选基线编译：copy-and-patch，函数粒度、微秒级编译、无优化 pass。平台允许时开，不允许时只解释。

**性能档位**（这是选这条路的真实账，不是卖点）：

以 LuaJIT 的优化 JIT 为 1.0，按 Deegen 论文的实测（44 个 Lua 基准）：

| 档位 | 相对 PUC Lua 解释器 | 相对 LuaJIT 优化 JIT |
|:--|--:|--:|
| PUC Lua 解释器 | 1.0 | 0.16 |
| LuaJIT 解释器 | 2.1 | 0.35 |
| 目前最好的解释器（LJR） | 2.8 | 0.46 |
| 最好的解释器 + baseline JIT（LJR） | 4.6 | 0.75 |
| LuaJIT 优化 JIT | 6.1 | 1.00 |

结论：纯解释器到不了 LuaJIT，这是一条构造性的线——JIT 的收益就是机器码，解释器每个操作付一次分派。能到的是"比 LuaJIT 的解释器更快"这一档；ψ 的静态类型（无装箱、无 tag 检查、单态调用、无守卫）应该比 LJR 再高一些，但那是设计目标，未实现。要越过 LuaJIT 必须有一条编译层。

**代价**：

- **相对现有 wasm 方案掉 3 到 4 倍**。Wasmtime 编出的代码约为 native 的 2.4 倍耗时（2026 年 libsodium 实测），解释器再掉一个档。wasm 引擎白送寄存器分配与指令选择，自建 VM 没有人替你优化。
- **"规格小到一个人能读完"破产**。值表示、调用约定、ABI、分配器、调试信息全部要自己拥有。这条与 [54](54-wasm-gc.md) 的收益正面互换。
- **浏览器里多一层**。浏览器不许执行自产机器码，VM 本身要编译成 wasm 再解释字节码，比直接发 wasm 多一次分派。除非 VM 与宿主核心同处一个 wasm 模块、脚本只作为数据进入——那正是这条路的形态，但边界仍是 wasm 导入。
- **两个发射器，两套调试路径**。"一份产物三个宿主"要改写成"一份 IR、三条出口"。
