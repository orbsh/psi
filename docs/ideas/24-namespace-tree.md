# 命名空间树

**状态**：候选
**一句话**：模块构成一棵树，`mod a { mod b { ... } }`，名字解析沿树上升；import 只是把树上的节点绑进当前作用域。

**动机**：树是最省解释的组织方式——读路径就知道东西在哪，工具（跳转、重命名、依赖分析）全部现成，[23](23-modules-as-values.md) 那种「模块是值」的代价（拓扑不可见、依赖注入太隐式）全部消失。

**形态**（若采用）：

```
mod shapes {
  struct Circle { let radius: Float }
}

mod report {
  use shapes::Circle
  def line c: Circle -> Text = ...
}
```

**代价**：多一套复用拓扑。树一旦承载语义，命名空间就同时是「代码组织」和「可见性边界」，想按功能切分与按目录切分冲突时要迁就树。另外「模块是值」能做的事（把模块当参数传、运行时选择实现）没了。对脚本规模的语言，树的收益可能仅在工具链。

**冲突**：[23](23-modules-as-values.md)。可以不互斥：树负责寻址，值负责传递——那样两边都留，规则数加一。

**若改掉会动到**：[22](22-three-containers.md)、名字解析顺序、[51](51-standard-wasm.md)（全程序编译仍成立，只是解析入口变了）。
