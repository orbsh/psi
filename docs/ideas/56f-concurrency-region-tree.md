# 并发：每线程一棵区域树，任务靠 scope 借

**状态**：候选
**一句话**：线程边界就是区域边界——每个线程有自己的区域树，跨树只传拷贝或消息；任务若要借用父区域的数据，唯一安全的形态是结构化并发（scope 保证任务先结束，区域后退出）。

**动机**：并发最容易弄脏内存层级的地方是「人走了，魂还在」——任务还在读一块已经擦除的区域。Rust 自己也是先有 detached `spawn`，再补 `std::thread::scope` 才让借用成为可能；同样的两步在这里更清楚，因为「谁比谁活得长」就是深度比较。

## 形态（三种，代价递增）

```
# A 结构化：scope 区域 ⊒ 任务区域，任务内可借用父区域
scope {|s|
  let data = load()
  s.spawn {|t| use data }      # 合法：任务保证在 scope 内结束
}                               # join 全部任务 → 擦除 scope 区域

# B 分离：捕获一律 move（拷进任务自己的根区域）
let h = spawn {|r| use data.clone}   # 没有 join 约束

# C 常驻 worker：根区域随进程，任务区随任务
pool.submit {|t| ... }
```

语法上关键的一点：**spawn 的闭包显式收一个区域句柄**（`|r|` / `|t|`）。这让闭包体内「分配落在哪」是写出来的，而不是从捕获推断出来的——推断在这里会逼出「闭包类型带区域参数」，那是最脏的一处。

## 类型判据：不需要新的 trait

- **能不能跨线程传**（≈ `Send`）：值里不持有指向**出生线程区域树**的指针。这正是 [56b](56b-depth-check.md) 那条深度比较，只是被比较的两个区域在**不同树**里。
- **能不能共享只读**（≈ `Sync`）：不可变值天然满足；要可变共享就只能走 root 区域里的 `Mutex` 类类型，它是唯一的内部可变性入口。深度规则管悬空，不管数据竞争——第二根轴只能靠「不可变」或「显式锁」。

所以「保持类型安全又不弄脏层级」的答案是：**把线程边界当作区域边界，复用同一条深度规则**。任何需要额外标记的地方（比如 `Send` 无法表达的那部分）都说明设计漏了一个逃逸点。

## 代价

- **结构化并发的限制是硬的**：任务不能比 scope 活得长，长驻后台任务只能用 B/C；而 A 的收益（借用、零拷贝）只有在任务短命时才拿得到。
- **B 需要引用计数**：分离任务的根区域寿命与 spawner 无关，谁负责擦？只能是 `JoinHandle`/`Task` 持有一个引用计数，最后一个引用走时擦除整棵树。这是整套设计里唯一必须引入 refcount 的地方——把它关在句柄类型里，别让区域本身可见。
- **通道缓冲住哪要定**：住接收方区域（发送时拷进去，发送方需要接收方的句柄）最省；住独立的共享区域（双方都引用）就要一块寿命由谁管的根。前者把「跨树引用」压成「传一个值」，后者是 shared region 的雏形。
- **C 的池化会把区域长寿化**：worker 的根区域常驻，任务不断在里面分配，等于把 arena 退化成「长期不擦的堆」——除非每个任务一个子区域、任务结束擦子区域。这条容易写错，也容易测出来（常驻区域的峰值）。
