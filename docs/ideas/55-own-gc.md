# 自建 GC 与分配器

**状态**：候选
**一句话**：语言自带分配器与回收器，值布局由语言定义——这样才有对象布局控制、短生命周期优化、以及不依赖宿主 GC 的产物。

**动机**：掌控内存才有可预测的性能。托管运行时（Go、C#、Swift）都自己管堆，理由相同：回收策略、对象头、指针压缩、分代都能按语言的值语义定制。对嵌入宿主场景，「宿主 GC 什么时候跑」不受语言控制也是一个真问题。

**形态**（若采用）：线性内存上自建堆，对象头 + 指针/句柄表，分代或引用计数；产物仍可以是 wasm 模块，只是要求宿主提供的只是线性内存。

**代价**：

- **「小」破产**：分配器、GC、对象布局、写屏障、逃逸分析全部要写，规格从一页变成一本书。这条直接冲掉 [54](54-wasm-gc.md) 的全部收益。
- **与不可变值语义的错配**：值不可变、无引用、无所有权，本就没有别名问题，自建 GC 的复杂度换不到安全收益。
- **跨边界**：线性内存里的对象要跨宿主边界，只能序列化，等于放弃「零拷贝共享」这个本来也不想要的东西。

**冲突**：[54](54-wasm-gc.md) 正面冲突。[56](56-hierarchical-arena.md) 是它的一个轻量变体。

**若改掉会动到**：整个内存章节、[44](44-text-repr.md)、[62](62-byte-boundary.md)、编译器与运行时的产物形态。
