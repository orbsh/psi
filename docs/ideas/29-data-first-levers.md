# 数据先行的硬杠杆与软杠杆

**状态**：在用（可改）
**一句话**：「接收者必须是聚合」不是禁令，是句法梯度；真正把数据逼到句首的杠杆里，三条是硬的（语法上做不到），一条是软的（做得到但别扭）。

**动机**：语言想引导的写法要拆成两类——能拦的和只能劝的。混在一起讨论会得出「所以设计得不彻底」这种空结论。

**形态**：

硬的（语法上做不到）：

- **类型必填**：没有 `any`、没有隐式转换；`let x = ...` 推不出类型就编译失败，逻辑没有地方寄放。唯一的通用值是 `Json`，它是有名字的普通 enum，不是 `any`，但确实把这口子软化了一格（见 [41](41-json-boundary.md)）。
- **穷尽匹配**：加一个变体，所有 `match` 立刻报错——形状一变，程序骨架被顶出来。
- **模块级只有声明**：没有顶层可执行语句，代码不能写成流水账，必须有家。

软的（做得到但别扭）：

- **没有自由函数**：每次调用都有一个主语位。`user.charge amount` 读着顺，`Payments.charge user amount currency date` 读着别扭——作者可以这么写（模块对象就是接收者），但写的时候自己看得见。这是 [18](18-named-functions.md) 的反面。

还缺一条：

- **构造受控**（[28](28-construct-controlled.md)）：现在外部也能写 `Circle { radius: ... }`，parse 造出的值和手搓的值同类型。

**代价**：软杠杆对「绕过者」完全无效，只提供可见性。硬杠杆里的「类型必填」把推断能力限制在不写标注就过不了的程度上，短脚本会嫌啰嗦；「模块级只有声明」让一次性脚本无法直接写。

**冲突**：[18](18-named-functions.md)、[28](28-construct-controlled.md)、[39](39-arity-cap.md)（硬拦参数个数是另一种做法）。

**若改掉会动到**：[18](18-named-functions.md)、[28](28-construct-controlled.md)、[41](41-json-boundary.md)、类型推断的野心。
